# IntDog 完整本地优先产品设计

状态：已完成对话设计审批，等待书面规格复核
日期：2026-09-01
对应英文：`2026-09-01-complete-local-first-product-design.md`

## 1. 目标

IntDog 必须同时达到两个硬门槛：

1. 行业情报功能形成可信、可持续、可审计的完整闭环；
2. Windows、macOS、Linux 用户可以下载各自安装包，完成首次启动、连接或交接 Agent、创建行业、运行首个任务、关闭重开和后台周期任务。

任一门槛未满足，产品状态均为 `NOT_READY`。三平台原生 CI 是发行硬门槛；公开 Beta 后的真实设备反馈属于补充证据，不替代原生 CI。

## 2. 决策与非目标

### 2.1 已批准决策

- 采用 local-first 模块化单体，不全盘重写，也不拆成微服务平台。
- 保留 React、Electron、FastAPI、SQLite 和 Python 研究核心，但重新划清边界。
- 增加跨平台后台 Worker，使窗口关闭后仍可执行周期任务。
- Agent 结果采用“人工复核 → 候选证据 → 自动核验 → 正式事实”的提升路径。
- Agent 按原生 CLI、API、MCP、任务包和受限自定义 CLI 分级接入，不虚报能力。
- 无 Agent、无 API Key 时仍能运行降级但真实的免密工作流。
- 每类信息源以 8–10 个高质量代表为目标；不满足可信度门槛时允许不足并公开缺口。
- 邮件推送保持禁用。

### 2.2 非目标

- 不提供 IntDog 云账户、云端同步或团队协作。
- 不要求所有 Agent 都能被 IntDog 直接执行。
- 不以固定 Top 10、固定中外比例或来源数量冒充行业完整性。
- 不把模型生成文本、单一媒体报道、自媒体内容或领导层 Post 直接写成事实。
- 本设计不授权删除生产数据、真实付费调用、commit、push、CI 触发或发布。

## 3. 架构

### 3.1 Desktop Shell

Electron 只负责窗口、系统托盘、首次引导、操作系统安全凭据、更新、后台服务安装和生命周期。它不承载研究逻辑，也不维护独立 Provider 清单。

### 3.2 Local API

FastAPI 是 React、Electron、后台 Worker、CLI 和外部 Agent 的唯一业务入口。请求与响应由 Pydantic 定义，OpenAPI 为权威契约，前端类型从契约生成。Local API 只绑定回环地址，使用随机会话令牌和来源校验。

### 3.3 Research Core

Python 核心负责来源发现、采集、规范化、去重、实体解析、产业链、证据图、覆盖规划和研究产物。核心不得依赖 Electron 或 React。

### 3.4 Background Worker

Worker 是独立、单实例、低权限进程。Windows 使用 Task Scheduler，macOS 使用 LaunchAgent，Linux 使用 systemd user timer。Worker 通过受保护的本地接口和持久任务仓库执行任务，不要求窗口常驻。

### 3.5 Data Store

SQLite 保存结构化状态、实体、关系、断言、事实、任务和审计。行业目录保存原始文档、必要快照、Markdown 和可视化 sidecar。写入使用临时文件与原子替换；数据库迁移单调、可备份、可回滚。

### 3.6 Agent Gateway

唯一能力 Manifest 描述 Agent 和 API Provider 的身份、地区、连接方式、执行等级、认证、Web 能力、结构化输出和可调度性。执行层使用显式适配器；未知 Provider 默认拒绝。

### 3.7 React Workbench

工作台按行业概览、每日情报、知识与实体、研究、产物、来源、任务、系统设置拆分。页面只消费强类型 API，不直接理解磁盘布局或 Provider 特例。

## 4. 权威数据流

唯一主数据流为：

`来源发现 → 原始采集 → 规范化与去重 → 候选证据 → 核验与冲突处理 → 知识图谱 → 研究产物`

Agent 导入必须从候选证据进入。任何 UI、CLI、调度器或适配器均不得绕过核验直接写入正式事实。

## 5. 数据与可信度模型

### 5.1 四层对象

- `Source`：发布者与入口，记录地区、类别、所有者、权威等级、访问方式、抓取健康度和选择理由。
- `Document`：原始文档，记录规范 URL、发布时间、作者、发布者、语言、采集时间、内容哈希和快照引用。
- `Assertion`：可验证断言，必须指向证据，并区分事实、观点、预测、公司披露、政策文本和二手转述。
- `Fact`：通过来源、时间、实体和冲突核验的知识。

可信度状态统一为：

`raw → candidate → corroborated / disputed / rejected → accepted`

重要争议不得用简单多数票覆盖。事实必须保留来源链和核验时间。

### 5.2 来源策略

政府、监管、统计、标准组织、公司原始披露和同行评审材料优先；新闻用于交叉验证；自媒体和领导层 Post 用于发现线索与观点。无法抓取但优质的来源进入手动访问推荐，不标记为采集成功。

每个来源类别以 8–10 个权威、知名、代表性发布者为目标。不同行业可以共享来源。系统不得为达到数量目标引入不可信来源；不足时显示缺口及原因。

中国来源占比不使用固定比例。系统测量中国与国外在子领域、产业链端点、实体和时间上的覆盖差异，优先补中国缺口，同时保留统一质量门槛。

### 5.3 来源发现、选择与持续审查

来源必须通过可审计的发现与审查流水线：

`查询规划 → 多轮检索 → 候选归一化 → 发布者身份核验 → 质量与代表性评估 → 覆盖与多样性审查 → 访问审计 → 激活或人工复核`

- 系统按行业、来源类别和产业链端点生成中英文查询族。查询族覆盖官方目录、监管与统计、协会、标准、公司披露、学术期刊、专业媒体、平台、自媒体和领导层账号。
- 每次来源建图至少执行两轮：第一轮建立权威基线；第二轮根据地区、端点、实体和来源类型缺口定向扩展。候选池必须大于最终 8–10 个入选目标。
- 停止条件同时要求覆盖门槛和边际收益收敛。只有连续两轮没有新增合格来源，或新增来源只重复既有发布者与覆盖单元时，才允许停止；预算、限流或网络中断必须记录为暂停理由，不能伪装成收敛。
- 每个候选来源记录发现查询、发现时间、发布者主体、所有权、原始或二手属性、地区、访问方式、历史稳定性、引用质量、更新频率以及选择或淘汰理由。
- 身份、所有权和 URL 验证通过的官方一手来源可以自动激活。媒体、平台、自媒体、领导层账号和其他个人来源必须先进入人工复核队列。
- 活跃来源定期重新审查。持续失效、所有权变化、内容农场化或长期无边际新增价值时，降为手动、备用或拒绝；历史文档和证据关系不得因此删除。
- UI 提供候选来源、审查记录、覆盖缺口以及选择或淘汰理由视图，并允许用户手动添加、重新评估和改变监测状态。

不足 8 个合格来源时，系统必须展示已执行查询、候选数、淘汰原因和剩余缺口，不能只返回空列表或低质量填充结果。

### 5.4 去重与开放世界覆盖

去重同时考虑规范 URL、内容哈希、近重复文本、事件、发布者和引用关系。归并重复文档时保留多来源关系，不删除证据链。

覆盖对象包括企业、研究组、政府机构、协会、投资机构、人物、产品、技术、标准和政策。系统报告“已知覆盖”和“未证明完整”，不以 Top 10 代替行业全景。

## 6. 产品工作流

### 6.1 首次启动

1. 检查数据目录、磁盘、后台服务、网络、可用 Agent/API 和凭据存储；
2. 选择无模型、已登录 CLI、API、MCP/任务包或受限自定义 CLI；
3. 创建行业，并依次通过信息源、产业链和实体覆盖门槛；
4. 运行一条可观察、可取消、可恢复的真实 bootstrap；
5. 完成后进入行业概览，重开后保留行业与任务状态。

无模型模式使用公开免密来源完成基础来源、文档、实体和产业链候选工作流。深度搜索、归纳和报告在连接 Agent/API 后启用，并明确显示能力差异。

### 6.2 行业概览

概览同时展示知识结构、产业链有向图、来源、文档、实体、证据质量和覆盖缺口。所有计数均链接到相应列表，不允许无依据的装饰性指标。

### 6.3 每日与周期情报

每日窗口为前一日 04:00 至当前系统时间。列表支持标题、类别、来源和发布时间排序，以及全选、多选和可恢复删除。来源显示实际网站、开发者、论文作者或自媒体名称。

周期支持周、月、季、半年、两年和五年。区间从上次成功边界开始；没有历史或不足一个周期时向前补足完整周期。长周期使用均匀时间桶，并同时满足总量、时间覆盖、发布者多样性和证据质量门槛。

### 6.4 研究与产物

研究助手、行业报告和 Intelligence Lab 使用统一产物模型：Markdown、引用、结构化断言、限制和可视化 sidecar。产业链、竞争格局、趋势、技术路线和事件影响可以生成有向图或时间图。

### 6.5 Agent 复核

用户必须能查看 Agent 结果中的每条断言和引用，再选择驳回、保留为观点或提交核验。人工通过不等于事实接受。引用可达性、来源身份、时间、实体和冲突检查通过后，才可提升为正式事实。

### 6.6 任务中心

任务中心显示阶段日志、心跳、进度、重试、取消、失败原因和恢复动作。涉及付费调用或首次新增凭据的后台任务必须等待用户确认。

## 7. 任务状态与恢复

任务状态为：

权威状态集合为 `queued / running / cancelling / paused / completed / partial / failed / cancelled / interrupted`。正常完成路径是 `queued → running → completed`；取消经过 `cancelling → cancelled`；`partial`、`failed`、`cancelled`、`interrupted` 均不得推进最后成功边界，`paused` 和可恢复的 `interrupted` 可重新排队。

每个阶段保存输入、时间窗、Provider、模型、进度、心跳、输出位置和失败分类。崩溃后按检查点恢复或安全失败，重复执行必须幂等。

错误分为配置、来源、数据、模型和系统五类。UI 显示原因、影响范围和可执行的下一步，不只显示 traceback 或无限 planning。

删除先进入 IntDog 回收站。永久删除需要明确二次确认。迁移前创建受控备份，失败自动回滚。行业导出包含 Schema 版本和校验值。桌面 App 与 Worker 使用单实例锁和任务租约，避免重复执行。

## 8. 安全与隐私

- API Key 只保存在操作系统安全存储，不进入 SQLite、DOM、API、日志、任务包或产物。
- 自定义 CLI 不经 shell；命令与参数使用白名单，限制路径、大小、运行时间和输出。
- MCP 默认只读，写入逐项授权。
- Agent 导入限制大小、Schema、行业、任务 ID、引用和目标路径，拒绝路径穿越。
- 日志在持久化前清理凭据，并限制单任务大小。
- 所有行业数据默认只保存在用户设备。

## 9. 测试覆盖合同

测试台账必须覆盖以下 P0 风险，并将每个风险追溯到可区分正误的测试与证据：

| 风险域 | 必须证明 |
| --- | --- |
| 首次使用 | 全新安装、无模型、CLI、API 路径可创建行业并完成首任务 |
| 数据可信度 | Source、Document、Assertion、Fact 不可越级；冲突与缺引用不能成为事实 |
| 来源发现与审查 | 中英文查询族、两轮扩展、候选归一、身份/所有权/URL 核验、人工复核边界和停止条件均可追溯 |
| 去重与覆盖 | URL、内容、跨来源重复、均匀时间桶和中国来源缺口策略符合合同 |
| Agent Bridge | 导出、导入、复核、候选核验、幂等与恶意输入均有确定结果 |
| 后台调度 | App 关闭、系统重启、重复唤醒、时区、夏令时、重叠和失败恢复 |
| 任务状态 | 取消、暂停、超时、崩溃、重试、幂等、心跳过期和部分写入 |
| 安全 | 凭据不泄露；路径穿越、命令注入和越权写入被拒绝 |
| 迁移恢复 | 旧库升级、失败回滚、备份恢复和旧版本兼容 |
| UI | 空状态、长文本、列表、下拉菜单、键盘、缩放、双语和错误恢复 |
| 资源边界 | 大文件、磁盘不足、超长输出、限流、断网和损坏数据安全失败 |
| 打包 | 冻结 sidecar、静态资源、安全存储和后台服务文件进入安装包 |
| 生命周期 | 安装、启动、运行、关闭、后台、重开、更新、卸载不误删行业数据 |

测试层级包括 Python 单元/属性/状态机/故障注入、FastAPI 契约与安全、React DOM 与可访问性、Electron renderer 首次流程、冻结 sidecar/Worker 集成，以及三平台原生安装包生命周期测试。少量公开免密来源可进入受控联网合同测试；付费 API 和真实 Agent 账户必须单独标注，不能用 mock 冒充通过。

## 10. 三平台发行门禁

1. 同一 Git revision 的 Windows x64、macOS arm64、Linux x64 工作流全部通过；
2. 每个平台独立生成安装包、校验值和测试报告；
3. 安装包完成首次流程、后台任务、关闭重开和数据持久化；
4. Windows/macOS 未签名时只能发布公开 Beta；稳定版必须签名，macOS 必须公证；
5. 任一 P0 风险未关闭，状态保持 `NOT_READY`。

## 11. 实施分解

本设计是系统级总规格，不能安全压缩为一个实施任务。后续按依赖顺序拆为五个独立子项目，每个子项目单独执行规格、计划、TDD、审查和验证：

1. **权威契约与 Agent 证据闭环**：统一响应 Schema、可读复核、候选证据与事实提升门槛；
2. **数据可信度与覆盖引擎**：四层对象、多轮来源发现与持续审查、来源组合、去重、冲突和开放世界覆盖；
3. **后台任务与恢复**：跨平台 Worker、系统调度、租约、检查点和恢复；
4. **完整用户工作流**：首次引导、行业管理、概览、每日、周期、研究、产物和任务中心；
5. **三平台产品化**：冻结资源、原生生命周期、签名状态、安装文档和 Beta 门禁。

每一子项目必须保持旧数据可迁移，并在完成后重新运行共享风险门禁。前一子项目的契约是后一子项目的输入。

## 12. 完成标准

只有同时满足下列条件才可称为完成：

- 五个子项目的批准合同均已实现；
- P0 风险台账每一行都有当次源码 revision 的执行证据；
- 无模型基础流程和至少一种已登录 Agent/API 深度流程均可运行；
- Agent 结果不能绕过候选证据核验；
- 来源建图具有可追溯查询、选择、淘汰、复核和收敛证据；
- App 关闭后周期任务仍能安全执行；
- 三个平台的安装包来自同一源码版本并通过原生 CI 生命周期；
- 文档、UI、API、安装包和发行状态相互一致；
- 未完成或未验证的能力明确标注，不以历史构建或 mock 结果替代。
